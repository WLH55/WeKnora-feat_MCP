## 3. Detailed Design & Implementation（Plan）

### 3.1 方案总览

四个后端修复 + 一个注册策略联动 + 一个前端 UX 防护，彼此独立可回滚：

- **B1 删除守卫**（防入口）：调用者删除后将不再拥有任何 active 成员关系 → 拒绝（跨空间超管豁免）。
- **B2 删除自洽**（修数据）：删除事务内把指向该空间的 `users.tenant_id` 清零。
- **B3 登录兜底**（自愈-登录）：home 空间已不存在 → 回退到第一个 active 成员关系（并持久化修复）；无则签发 tenantless token。
- **B4 中间件降级**（自愈-会话）：JWT 指向的空间已不存在 → 按 tenantless 处理（白名单放行 / 其余 409 TENANT_REQUIRED），替代现行 401。
- **B5 注册策略联动**：自助创建空间策略关闭时，公开注册默认 `tenantless`，不再发放个人空间。
- **FE1 前端防护**：最后一个空间时禁用删除按钮 + 提示（后端为权威，前端仅 UX）。
- **F2 文案微调**（P3）：去掉"请检查网络"的误导。

**遗留数据**：B3+B4 上线后已困住账号自愈（重登即恢复 tenantless 会话，可接受邀请），无需数据迁移。修复上线前应急手段（运维手册）：`UPDATE users SET tenant_id = 0 WHERE tenant_id = <已删除空间ID>;`。

### 3.2 File Changes & Signatures

#### [B1] 删除守卫

- `internal/errors/errors.go`
  - 新增 `func NewLastWorkspaceDeleteDeniedError() *AppError`（仿 `NewTenantCreationDisabledError()`，code 形如 `LAST_WORKSPACE_DELETE_DENIED`，跟随本文件既有 code 风格）。
- `internal/handler/tenant.go` → `func (h *TenantHandler) DeleteTenant(c *gin.Context)`（`tenant.go:1047`）
  - 解析 id 后、调 `h.service.DeleteTenant` 前插入：
    1. `caller, err := h.userService.GetCurrentUser(ctx)`；失败 → 401（对齐 `CreateTenant` 的写法）。
    2. 若 `caller.CanAccessAllTenants == true` → 跳过守卫（超管管理目录不受影响）。
    3. 若 `h.memberService == nil` → 跳过守卫（沿用本仓库 nil-skip 惯例）。
    4. `memberships, err := h.memberService.ListByUser(ctx, caller.ID)`；统计 `status == active && tenant_id != id` 的数量；为 0 → `c.Error(errors.NewLastWorkspaceDeleteDeniedError())` 并 return。

#### [B2] 删除事务清理 home 指针

- `internal/application/repository/tenant.go` → `func (r *tenantRepository) DeleteTenant(ctx context.Context, id uint64) error`（`tenant.go:125`）
  - 事务内、删除 tenant 行之后追加：
    `tx.Model(&types.User{}).Where("tenant_id = ?", id).UpdateColumn("tenant_id", nil)`
  - **必须写 NULL 而非 0**：`users.tenant_id` 为可空列且带 PostgreSQL FK（`internal/application/repository/user.go:115-126` UpdateUser 对 tenantless 用户即显式存 NULL；写 uint64(0) 会违反外键约束）。GORM 扫描时 NULL → 0，语义一致。
  - 用 `UpdateColumn` 跳过 hooks/`updated_at`（修复性写入，不语义化为用户资料变更）。
  - *（Execute 阶段修订：原 Plan 写 `UpdateColumn("tenant_id", 0)`，实现时发现 FK 约束，按本节修订执行。）*

#### [B3] 登录 home 空间存在性校验

- `internal/application/service/user.go` → `func (s *userService) homeOrFirstMembershipTenant(ctx context.Context, user *types.User) uint64`（`user.go:779`，签名不变）
  - `user.TenantID != 0` 时先 `s.tenantService.GetTenantByID(ctx, user.TenantID)` 校验存在；失败（record not found）→ warn 日志一次 → `return s.resolveFirstMembershipTenant(ctx, user)`（命中成员关系时该方法已负责持久化修复；无成员关系返回 0）。
  - `s.tenantService == nil` 时维持现状（直接返回 `user.TenantID`）。

#### [B4] 中间件 tenantless 降级

- `internal/middleware/auth.go`（`authenticateJWTUser` 的空间解析段，`auth.go:226-239`）
  - `GetTenantByID(targetTenantID)` 失败时：由 401 改为 warn 日志 + 降级恢复，按序尝试：
    1. 先调既有 `resolveFirstMembershipTarget(ctx, user, memberService, tenantService)`（`auth.go:276-277` 注释的 tenantless 会话自愈路径，已有单测覆盖）——若用户已有 active 成员关系，直接以该空间恢复会话；
    2. 未命中 → 置 `targetTenantID = 0`，复用现有 `targetTenantID == 0` 分支语义：`isTenantOptionalAPI` 命中 → `attachTenantlessUserContext` 放行；未命中 → 409 `TENANT_REQUIRED`。
  - 实现建议：把现有 `== 0` 分支与该降级路径收敛到同一处理块，避免两份白名单逻辑漂移。
  - 保持不变：`X-Tenant-ID` 显式切换到不存在空间的 400 行为（`resolveTargetTenant` 内）。
  - 安全性：无提权——用户仍需通过 JWT 认证；死空间下所有空间级数据本就不可达，tenantless 仅放开身份级接口。

#### [B5] 注册策略联动

- `internal/handler/auth.go` → `func (h *AuthHandler) resolveDefaultTenantMode(ctx context.Context) types.TenantProvisioningMode`（`auth.go:107`）

  - 语义：自助创建关闭的部署里，公开注册不再发放"注册时给、丢掉后不让再建"的个人空间；新注册用户落在引导页等邀请，与策略自洽。

### 3.4 Validation 标准（验收）

1. Owner 删除自己唯一空间 → 4xx 明确错误码，前端按钮不可点。
2. 删除任一空间后，无任何 `users.tenant_id` 悬空指向该空间（事务保证）。
3. 人为制造悬空 `users.tenant_id` 后重登 → 签发 tenantless 或首个有效成员空间 token；`/auth/me`、`/me/invitations` 可用。
4. JWT 指向已删空间（存量会话）→ 身份级接口放行（tenantless），空间级接口 409 `TENANT_REQUIRED`，绝无 401 死循环。
5. 自助创建关闭的部署：公开注册不再创建个人空间（注册后直接进引导页等邀请）。
