## 2. Research Findings

- 事实与约束:
  - 现状：`WEKNORA_API_KEY` 启动时读一次 env（L32），写入线程本地 `requests.Session` 默认头（L149-152），所有出站请求同一身份；MCP 协议层无「客户端凭证」概念，需借 HTTP 头传入
  - 鉴权中间件 `MCPAuthMiddleware`（L60-105）已拦截所有 http/sse 请求并解析 `Authorization: Bearer` 与 `X-MCP-Auth-Token` —— 是植入每用户 key 提取的天然位置
  - 上下文传播机制：http(Streamable) 传输下每个 `tools/call` POST 在自身请求任务内处理；同步工具经 anyio `to_thread` 执行（自动拷贝 contextvars）；但 `chat`/`agent_chat` 用 `run_in_executor`（L878/L949）**不传播 contextvars**，需显式 `contextvars.copy_context().run` 包装
  - `requests` 语义：`session.request(..., headers=...)` 按请求合并覆盖 session 头 —— 用按请求头覆盖，**绝不改写 session 默认头**（线程本地 session 被多请求复用，改写会造成用户间 key 串号）
  - 出站需覆盖的三个点：`_request()`（L160-186）、`_consume_sse_stream()`（L469 `self.session.post`）、`create_knowledge_from_file()`（L313-322 复制头后直发 `requests.post`）
  - 后端权限模型现成：能力位 + KB 白名单 + 会话按 `SessionOwnerIDFromContext` 归属隔离（session.go:352 已验证），不同 key = 不同归属桶
  - 旧 spec 实证（2026-09-02）：网关只认 `MCP_SERVER_AUTH_TOKEN` 一个口令，其余 key 401；per-key 权限在 MCP 链路失效
- 现状链路:
  `Claude(Bearer=sk-A) → 网关:校验≠口令→401 / =口令→放行但出站仍用 env key → 后端(单身份)`
  目标链路:
  `Claude(Bearer=sk-A) → 网关:非口令→按每用户key放行并记ContextVar → WeKnoraClient按请求选key → 后端(身份=sk-A, 白名单生效, 会话独立)`
- 风险与不确定项:
  - SSE 老传输：SDK 可能在 SSE 长连接任务而非 POST 任务内处理消息，ContextVar 未必可达 —— 缓解：本特性承诺 http 传输；sse 下无 override 时回落 env key（不劣于现状），文档注明
  - 未知 Bearer 直接放行给后端校验：网关从「口令门卫」变「透传验真」，无效 key 由后端 401 兜底；网关侧仅做格式校验（长度/可打印）挡明显垃圾输入，避免日志噪声
  - key 泄露面：per-user key 仅存于请求期内存与出站头；须确认所有日志路径不打印（含 `_debug_events`、异常包装）

## 2.3 能力位映射研究结论（MCP 工具 → 后端路由 → 所需能力）

验证机制（三层，逐请求执行）：① auth 中间件按 SHA-256 哈希查 `tenant_api_keys`（吊销/过期即时 401）→ ② `APIKeyRouteAuthorizer` 按路由表查策略（能力 OR full_access，未声明路由默认拒绝）→ ③ KB 白名单（`AllowsKnowledgeBase` 等）对 KB 级路由兜底。

| chat / agent_chat / create·get·list·delete_session | /knowledge-chat、/agent-chat、/sessions（routes_chat.go:106/112/51） | chat |
| list_agents / get_agent | /agents（routes_agent.go:26） | read_agents ∨ chat ∨ manage_agents |

## 3. Innovate (Options & Decision)

### Option A：入站双通道 + ContextVar 按请求覆盖（本 Plan 采用）
- 做法：中间件识别 Bearer/X-WeKnora-Key 中的个人 key 存入 `ContextVar`；`WeKnoraClient` 出站时 `ContextVar 或 env` 按请求决定 `X-API-Key`；`chat`/`agent_chat` 用 `ctx.run` 包装穿透线程池
- Pros: 单部署多用户；客户端兼容性最好（token 字段或自定义头都行）；`MCP_SERVER_AUTH_TOKEN` 保留为主凭证（向后兼容）；stdio 完全不受影响
- Cons: 需理解 contextvars 传播边界（已在 §2 标注并测试覆盖）；SSE 老传输不承诺

### Option B：每用户一个网关容器
- Pros: 零代码改动
- Cons: key 数=容器数；权限仍折叠；运维成本线性涨 —— 已被用户否决（旧 spec Option B 同款）

### Decision
- Selected: Option A（= 用户选定的「方案二」= 旧 spec 的路 A，并补齐上下文传播与双通道设计）
- Why: 2026-09-13 用户明确选择方案二；结合旧 spec 路 A 语义与客户端兼容性考量

### Skip (for small/simple tasks)
- Skipped: false
- Reason: 涉及鉴权语义变更与并发上下文传播，需留决策记录

## 9. Appendix: ClawHub「WeKnora」skill 与 mcp-server 对比（背景参考）

> 2026-09-13 侧聊调研存档。该 skill 是本 spec 所改网关之外的**另一条 WeKnora REST 接入路径**，与正文改造互补，无代码交叠。

### 9.1 skill 是什么 / 怎么装

- ClawHub（OpenClaw 技能市场）上的 SKILL.md 格式技能：slug `weknora`，发布者 lyingbug，v1.0.1，MIT-0。内容本质是一份「让 Agent 用 curl 直调 WeKnora REST API」的操作手册（端点决策表 + 工作流 + 错误处理约定）。
- 安装（本机已有 clawhub CLI v0.7.0）：`clawhub install weknora --workdir "C:\Users\WLH\.zcode" --dir skills`，落在 `~/.zcode/skills/weknora/`。
- 配置：环境变量 `WEKNORA_BASE_URL` + `WEKNORA_API_KEY`（即「API 集成」页的地址与 Key）。

### 9.2 能力对比

| | ClawHub skill（12 个 REST 端点） | mcp-server（30 个 MCP 工具） |
|---|---|---|
| 会话/问答（chat/agent_chat） | ❌ 无 | ✅ |
| 智能体发现 | ❌ 无 | ✅ list/get_agent |
| 知识库创建/删除 | ❌ 无 | ✅ |
| 模型管理 | ❌ 无 | ✅ |
| Wiki 检索 | ❌ 无 | ✅ |
| 文档上传（文件/URL/Markdown） | ✅ | ✅ |
| 解析进度轮询 + 失败 reparse | ✅（工作流内置闭环） | ❌（只有 list/get） |
| **编辑 Markdown 知识** | ✅ `PUT /knowledge/manual/:id` | ❌（工具面刻意不含 update） |
| 删除知识/分块 | ✅ 单条删知识 | ✅ 知识+分块 |
| 检索 | ✅ 单库 hybrid-search + 跨库 knowledge-search | ✅ hybrid_search（单库） |
| 部署形态 | 零部署，Agent 进程内直接 curl | 独立容器/进程（MCP 协议） |

skill 封装的 12 个端点：list/view 知识库、上传文件、导入 URL、写 Markdown、查解析进度、分页浏览、读详情、编辑 manual、删知识、单库 hybrid-search、跨库 knowledge-search、reparse（仅见于错误处理建议）。

### 9.3 与本 spec 主题（多用户隔离）的关系

- skill 的 Key 跟着**进程环境变量**走：每个开发者各设各的 `WEKNORA_API_KEY`，per-key 能力位/KB 白名单**天然生效**，不存在网关折叠身份问题——这正是本 spec 为共享 mcp-server 解决的同款问题（§2.3 的三层校验对 skill 同样逐请求生效）。
- 分工建议：日常「边干活边喂知识库 + 随手检索」用 skill（零部署、有编辑/reparse）；需要 RAG 问答/智能体会话或集中托管接入用 mcp-server（本 spec 改造后同样支持多用户各持己 Key）。
