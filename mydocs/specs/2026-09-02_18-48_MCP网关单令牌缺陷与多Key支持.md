## 1. Requirements (Context)

- **Goal**: 让前端「API Keys」页面创建的多把 key 能**同时**接入 MCP 客户端，且每把 key 的能力（capabilities）与知识库白名单在 MCP 链路上**真实生效**
- **In-Scope**:
  - `mcp-server/`（Python 网关）认证/转发逻辑改造 **或** 容器化多实例方案（二选一，见 §3）
  - ZCode 客户端配置新增 `weknora_2` MCP 条目
- **Out-of-Scope**: WeKnora Go 后端、前端 UI、平台级（platform）API Key 体系

## 2. Research Findings（缺陷本体）

### 2.1 缺陷一句话

mcp-server 网关是「**单共享口令 + 固定后端身份**」设计：客户端 Bearer 只和一个静态环境变量做字符串比对，且客户端 key **不透传**给后端——导致前端创建的多把 API Key 无法同时用于 MCP，per-key 权限模型在 MCP 链路上完全失效。

### 2.2 证据链（file:line）

| # | 事实 | 位置 |
|---|---|---|
| 1 | 网关是独立 Python 服务（非 Go 后端组件），docker-compose `mcp` 服务，容器 `WeKnora-mcp`，宿主机 8082→容器 8000 | `docker-compose.yml`（mcp 服务块） |
| 2 | 门禁 = 单令牌比对：`MCPAuthMiddleware` 用 `secrets.compare_digest(provided, token)`，token 来自 `MCP_SERVER_AUTH_TOKEN`；不匹配 → 401 `{"error":"unauthorized"}` | `mcp-server/weknora_mcp_server.py:64-99`（比对在 :87，401 在 :88）、`:45-47` |
| 3 | key 不透传：`WeKnoraClient` 对后端固定 `X-API-Key: <WEKNORA_API_KEY>`（环境变量注入），所有客户端共享同一后端身份 | `mcp-server/weknora_mcp_server.py:151`（header）、`:32`（env 读取） |
| 4 | WeKnora 后端**无原生 MCP 服务端点**：`/mcp-services` 是 WeKnora 作为 MCP 客户端的管理路由；MCP 接入只能走上述网关 | `internal/router/routes_infra.go:125-146` |
| 5 | `.env` 现状：`WEKNORA_API_KEY` 与 `MCP_SERVER_AUTH_TOKEN` 为同一字符串 sk-Uzj9...（DB id=3「工作知识库MCP」，18 能力全开、知识库范围空 = 全部） | `.env:587-589`；`tenant_api_keys` id=3 |
| 6 | 新 key sk-H8Ho... = DB id=5「测试只读」（retrieve + read_agents，KB 白名单 = [977afbcb → 案例设计知识库]），有效未吊销未过期 | `tenant_api_keys` id=5 |
| 7 | **实证**：sk-H8Ho 直连后端 8080（`X-API-Key`）→ 200，仅见「案例设计知识库」（白名单精准生效）；同 key 经网关 8082（Bearer）→ 401（被门禁拦截，因为 ≠ 暗号） | 2026-09-02 curl 对照实验 |

### 2.3 影响

- 所有 MCP 客户端（ZCode / Claude Desktop / Cursor 等）在后端**折叠为同一身份**（id=3 全能力 key）
- 前端「API Keys」页面的能力/白名单模型只对直连 REST 的调用方生效，MCP 链路享受不到
- 现状下每多接入一把 key，需要多起一个网关容器（workaround，见 §3 Option B）

### 2.4 风险与不确定项

- 路 A 改造后，网关从「口令门卫」变为「代理验真」：任意字符串都会被转发后端校验，需处理 401 透传路径与日志噪声
- 路 B 方案下，每个容器 env 都持有一把真实 key，泄露面随 key 数量线性增长
- 命名注意：新 key 名为「测试只读」但具有 `read_agents`；白名单指向「案例设计知识库」而非「工作知识库二」（见 §0 第 2 条）

## 3. Innovate (Options & Decision)

### Option A：网关透传改造（推荐）

- 改动点：`MCPAuthMiddleware` 放宽为——Bearer == `MCP_SERVER_AUTH_TOKEN` → 沿用 `WEKNORA_API_KEY`（**向后兼容**，现有 weknora 连接不受影响）；否则将 Bearer 作为 `X-API-Key` 透传给后端，由后端校验真伪并强制能力/白名单；`WeKnoraClient` 支持按请求选择 key
- Pros: 一个网关服务任意多把 key；per-key 能力/白名单端到端生效；新增 key 零部署动作；与前端「API Keys」页面设计意图打通
- Cons: 需改 `weknora_mcp_server.py` 并重建容器；401 透传的错误路径与日志需处理

### Option B：每 key 一个网关容器

- 改动点：docker-compose 增加 `mcp2` 服务（8083 端口），`MCP_SERVER_AUTH_TOKEN` 与 `WEKNORA_API_KEY` 均设为目标 key；ZCode 增加 `weknora_2` → `http://localhost:8083/mcp`
- Pros: 零代码改动，立即可用
- Cons: key 数量 = 容器数量；权限模型依旧是「折叠为单身份」；多把真 key 散布在 env 中
