## ① 挑战：问题与场景

**我的场景**：我在【部门名称，如：数据中台】担任【岗位，如：研发工程师】，公司日常协作主要在钉钉上。真正有价值的知识——排障思路、历史决策、接口约定、踩坑记录——散落在钉钉群聊天记录、个人电脑和各类网盘里，从来没有一个"能问、能搜、能管权限"的统一归宿。

**四个具体痛点**：

| # | 痛点 | 具体表现 |
|---|------|---------|
| 1 | 找不到 + 重复问 | 文档散落在钉钉群、个人本地、各类网盘，搜索基本靠"问人"；老员工被重复问题反复打断 |
| 2 | 新人上手慢 | 业务逻辑、系统设计、历史踩坑都在老员工脑子里，靠口口相传，人员一流动就断档 |
| 3 | 跨部门知识不流通 | 需求文档、数据口径、业务规则各管各的，跨部门协作要先花半天"对齐常识" |
| 4 | 数据安全合规约束 | 内部文档不能投喂公网 AI 产品，一直缺少私有化部署的知识库方案 |

落到我自己的研发工作上，还有三个更具体的切肤之痛：线上问题解决后，排查思路留在群聊和个人脑子里，别人下次踩同样的坑还要从头再来；AI 编码工具（GitHub Copilot、Claude Code 等）很强，但不知道公司内部的服务架构、历史决策和踩坑记录，生成的代码经常"不符合我们的规矩"；产品和同事上传的需求文档、接口文档，开发要花很久才能检索到某个功能的接口设计或需求设计。

**过去是怎么处理的**（与"现在"形成对比的关键）：

- **靠问人**：找不到就问老员工，一个问题往往要打断对方 15~30 分钟，同样的问题隔几周换个人再问一遍
- **靠归档**：共享网盘 + 钉钉群置顶，靠文件名和目录人工整理，一旦没人维护就慢慢失效
- **靠带人**：新人上手靠老员工口口相传，交接质量完全取决于带的人和时间
- **公网 AI 用不了**：效果虽好，但公司规定内部文档不得上传公网服务，合规红线绕不过去

**希望解决后达到的效果（货币化目标）**：

- 重复答疑量下降约 70%，老员工每周被打断时间从【X 小时】降到【Y 小时】，年化释放约【Z 人日】
- 新人独立上手周期缩短 30%~50%，按每年【N】名新人计，节省人力成本约【　】万元/年
- 单次查找历史文档/接口约定的平均耗时从约 20 分钟降到 2 分钟以内

## ② 我是如何解决的：私有化部署 WeKnora + 两项二次开发

### 2.1 选型：为什么是 WeKnora

市面上的 AI 知识产品要么是个人工具（无权限体系），要么是公网 SaaS（数据出内网），都打不中上述四条痛点。我深度调研并本地部署了**腾讯开源的 WeKnora**（github.com/Tencent/WeKnora，MIT 协议——可免费商用、可二次开发，当前版本 v0.8.0，社区活跃，入选 Trendshift 开源趋势榜），完成了从权限模型到文档摄入的实测后正式落地。

一句话定位：**把散落的文档变成可检索、可推理、持续演化的知识资产**。打动我们的三大核心能力：

| 能力 | 说明 | 对应场景 |
|------|------|---------|
| RAG / Wiki / FAQ 三种知识库 | 同一份文档可选不同知识库形态：RAG 检索增强问答，答案带原文溯源（点击引用可跳转文档出处）；Wiki 模式由大模型把原始文档蒸馏成结构化、互相链接的 Wiki 页面 + 知识图谱；FAQ 模式维护结构化问答对 | RAG：日常查口径、查制度、查历史决策；Wiki：把成堆散文档变成"公司内部维基百科"；FAQ：构造结构化问答库，适合 AI 客服 |
| 智能体 | 可定制提示词的 AI 智能体，ReAct 多步推理，自主编排"知识检索 + MCP 工具 + 联网搜索" | 复杂任务：查数、比对、汇总；也可绑定钉钉机器人、网页挂件对外服务 |
| 多租户权限控制 | 部门级空间隔离 + 四角色 RBAC + 跨部门共享空间（权限三维取最低）+ API Key 细粒度能力授权 + 审计日志 | 让它区别于个人 AI 工具、能进企业的前提：谁能看什么、谁能改什么、做了什么可查 |

**第五步：权限隔离——AI 检索也不能越权。**

空间内部靠上面的四角色 RBAC；跨部门靠共享空间：把知识库共享到共享空间供其他部门访问，可设只读或可编辑。共享空间的规则（我们实测验证过）：

- 共享空间不拥有任何资源——它只是一张"通行证发放名单"：知识库永远留在源部门，跨部门访问用的还是源空间的模型配置，存储也计入源空间配额
- 共享空间的成员是空间（部门）而非个人：一个空间加入后，全员自动继承该空间在共享空间里的角色
- 实际权限三维取最低：min（① 共享时选择的只读/可编辑，② 本部门在共享空间中的角色，③ 个人在本部门中的角色）——任何一维是短板，结果就是短板；第三维是硬天花板：在本部门只是访客的人，无论共享空间给多高，一律压回只读
- 拥有编辑权限的成员即可将知识库共享到共享空间
- 共享空间的管理（创建/邀请/改角色）走另一条线，只对本部门管理者及以上角色开放，与知识库内容的读写权限互不混用

![共享空间](https://cdn.nlark.com/yuque/0/2026/png/28467887/1789358156554-76e8a2eb-e9e5-410c-b99f-1d7896e40dbe.png)

还有一个关键问题：通过 API / MCP 访问时不携带空间成员的个人身份，如果全组共用一把 API Key，等于"谁拿到 key 谁就有全部权限"。解决办法是**给每位同事签发独立的 API Key 并逐项勾选能力范围**，同事接入 MCP 工具时使用自己的 key——实现"不同的人、不同的访问权限"。

## ③ 使用中遇到的新问题与解决

**问题一：官方不支持钉钉文档同步，而我们公司的主协作平台就是钉钉。**
WeKnora 官方数据源只有飞书、Notion、语雀、RSS。我调研了钉钉开放平台 API：文档只提供块（blocks）级读取接口、没有整篇导出接口，也没有文档变更事件。于是基于 WeKnora 的数据源连接器框架二次开发：自写 block → Markdown 转换器，按修改时间轮询做增量同步；支持按钉钉知识库整库同步和按链接同步单篇文档。开发耗时【X 人日】，已在内部版本稳定运行。

**问题二：API Key 不区分人，AI 接入存在越权风险。**
原生的 API / MCP 接入无法携带个人身份，共享一把 key 意味着权限失控。二次开发了**按人 API Key 透传与校验**：每人一把独立 key、逐项勾选能力范围，服务端按 key 鉴权，配合空间 RBAC 实现"AI 同人同权"——同事 A、同事 B 各自用各自的 key 接入 MCP，权限互不可见。

**问题三：部署运维的小坑（各一句话）。**
容器沙箱需要访问 Docker 引擎，Docker Desktop 下默认 socket 权限不足，调整挂载与启动脚本后解决；前端容器偶发运行旧版本，排查发现本地构建脚本少跑一步会被 Docker 层缓存复用旧镜像，固化构建流程后解决。

## ⑤ 其他人什么场景下也可以用这套方法

**产品经理：历史决策不再失忆。** "这个功能当初为什么这么做？"——过去要翻三个月前的群聊、问三个当事人。把 PRD、评审纪要、用户反馈、竞品分析批量导入 WeKnora，用 Wiki 模式自动蒸馏成结构化、互链的产品知识库和知识图谱；评审会前让智能体检索"这个需求历史上讨论过什么"，带出处。涉密内容放独立知识库收紧权限，需要给研发看的 API 文档库通过共享空间以只读方式共享——横向协作走共享通道，纵向的裁撤讨论、定价策略依然只有本部门可见。

## ⑥ 其他说明

**为什么不用别的方案**：【待填：实际对比过的方案，如公网 AI 知识库 SaaS（数据出内网，合规不过关）、纯人工维护的 Confluence/Wiki（靠人写、没人搜，历史已证明会荒废）、从零自研（投入远超收益）】。

**安全与合规**：全程私有化部署，数据不出内网；模型凭据 AES-256-GCM 加密存储；API Key 细粒度授权；操作审计日志可查——这是我们敢于把内部知识交给 AI 检索的前提。

**成本透明**：软件零 license 费用（MIT 开源协议）；主要成本是服务器与模型 API 用量，一次性成本是搭建与二开人力，详见 ④ 表。

**后续计划**：【待填，如：推广更多部门接入、用 Langfuse 观测用量与优化检索、沉淀运维 SOP 等】。

### A.2 知识库管理

知识库分文档型与问答型（FAQ）；文档型创建时可选 RAG / Wiki 模式：

- **RAG**：向量相似度检索，适合制度、方案、复盘等非结构化文档
- **Wiki**：由大模型自动生成互链 Wiki 页面，之后按页面元数据做关键词匹配，支持多跳检索
- **FAQ**：结构化问答对，适合客服类高频问题

### A.3 智能体配置要点

内置四个智能体，均可自定义编辑，也可新建。几个关键配置项：

1. **类型**：推荐"智能推理"——检索步骤严谨、支持多跳；"快速问答"只做一次检索
2. **自定义提示词**：定义智能体的人设与回答规范
3. **模型配置**：推理、多模态等可分别指定模型
4. **问题推荐**：对话界面的推荐问题，可由知识库自动生成或人工配置
5. **指定可访问的知识库**：划定检索范围
6. **工具配置**：联网搜索、图片识别、MCP 服务连接、Skill 等能力开关
7. **发布渠道**：IM 机器人 / 网页嵌入 / API（见正文 2.4）
